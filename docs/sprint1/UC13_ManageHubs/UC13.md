## Scope and evidence

The official [Case Study](https://drive.google.com/drive/folders/14cJnJ9_AhfFeWIxvzuRefNueToF5RyNF) states that administrators maintain hubs, each hub has limited kitchen capacity, and a busy hub stops taking new orders while customers are encouraged to use quieter hubs. The 03 November 2026 Final Project Requirements list **UC13 — Manage hubs and kitchen capacity** as an Admin CRUD candidate. However, Team F4's Part 1 proposal and existing workbook assigned **UC14 — Manage brands and menu items** to this author. The team must confirm the ownership change. The Case Study does not define capacity units/thresholds, operation-level permissions or deletion policy; those details remain **To Confirm**.

## Fully developed use case description

| Field | Description |
|---|---|
| Goal | Maintain hub records and their kitchen capacity settings so authorized staff can inspect and manage the information used by hub operations. |
| Primary actor | Admin, as identified in the official Final Project Requirements. Operation-level permissions remain **To Confirm**. |
| Trigger | An authorized user selects hub and capacity management. |
| Stakeholders | Admin needs accurate hub data; Kitchen Staff need a usable operational capacity setting; Customers and Managers depend on reliable hub information and workload reporting. |
| Preconditions | The actor is authenticated and authorized for the requested operation (**Proposed / To Confirm**). For read, update, or delete, the target hub exists. The definition and unit of kitchen capacity are **To Confirm**. |
| Success postconditions | Create: a new hub and its submitted capacity setting are recorded. Read: hub details are returned without mutation. Update: approved changes are recorded. Delete: the system applies the confirmed removal or archival policy and returns its result (**policy To Confirm**). |
| Minimal guarantee | Validation or authorization failure leaves stored hub data unchanged. A failed write reports failure; if the response is lost after a write, the actor reads the hub again before retrying. |

### Main success scenario — Create a hub

1. The actor opens hub management. The system displays the hubs the actor is permitted to view.
2. The actor selects **Create**. The system presents the required hub and capacity inputs.
3. The actor submits hub details and a kitchen capacity setting.
4. The system checks Create permission, required data, capacity validity and any confirmed uniqueness rules.
5. The system records the validated hub and capacity setting.
6. The system returns the new hub identifier and recorded details.

The exact validation thresholds and uniqueness rules in step 4 are **To Confirm**. Only one CRUD operation executes per selection; the other operations are alternative flows.

### Alternative flows

- **A1 — Read:** At step 2, the actor selects a hub for Read. The system checks Read permission and existence, then returns its details and capacity setting without mutation.
- **A2 — Update capacity or hub details:** At step 2, the actor chooses Update. The system shows current values, accepts edits, checks Update permission, existence, validity and concurrent changes, then records and returns the updated record. Whether capacity changes affect existing orders is **To Confirm**.
- **A3 — Delete or archive:** At step 2, the actor chooses Delete. The system checks Delete permission, existence, dependencies and the confirmed retention policy before returning the outcome. The choice between hard deletion, soft deletion and blocking removal is **To Confirm**; this draft does not prescribe one.
- **A4 — List/search:** At step 1, the actor filters the hub list. Search fields, pagination and sorting are **Proposed / To Confirm**.

### Exception flows

- **E1 — Unauthorized:** At any operation, the actor lacks the required permission. The system rejects the request without disclosing or changing protected hub data.
- **E2 — Invalid input:** At step 4 or A2, a required value is absent or a capacity value fails its confirmed validation rule. The system identifies the invalid field and makes no change. Capacity units and limits are **To Confirm**.
- **E3 — Hub not found:** A selected identifier is absent or unavailable. The system reports that the hub cannot be found and asks the actor to refresh the list.
- **E4 — Duplicate or conflicting record:** A confirmed unique identifier conflicts with an existing hub, or another user changes the record before the write. The system rejects the stale/conflicting write and returns the current state where authorized. Uniqueness keys and concurrency policy are **To Confirm**.
- **E5 — Removal blocked:** At A3, a confirmed dependency or retention rule prevents Delete. The system explains the block and preserves the record. Which dependencies block removal is **To Confirm**.
- **E6 — Persistence or response failure:** The system reports a failed write. If a response is lost after a possible write, the actor reads the record before retrying to avoid duplicate creation or unintended repeated changes.
