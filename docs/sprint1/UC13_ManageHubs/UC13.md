## Fully developed use case description

| Field | Description |
|---|---|
| Goal | Maintain hub records and their kitchen capacity settings so authorized staff can inspect and manage the information used by hub operations. |
| Primary actor | **Proposed / To Confirm:** Admin. The source material mentions admins managing system information but does not explicitly assign UC13 permissions. |
| Trigger | An authorized user selects hub and capacity management. |
| Stakeholders | Admin needs accurate hub data; Kitchen Staff need a usable operational capacity setting; Customers and Managers depend on reliable hub information and workload reporting. |
| Preconditions | The actor is authenticated and authorized for the requested operation (**Proposed / To Confirm**). For read, update, or delete, the target hub exists. The definition and unit of kitchen capacity are **To Confirm**. |
| Success postconditions | Create: a new hub and its submitted capacity setting are recorded. Read: hub details are returned without mutation. Update: approved changes are recorded. Delete: the system applies the confirmed removal or archival policy and returns its result (**policy To Confirm**). |
| Minimal guarantee | Validation or authorization failure leaves stored hub data unchanged. A failed write reports failure; if the response is lost after a write, the actor reads the hub again before retrying. |

### Main success scenario

1. The actor opens hub management. The system displays the hubs the actor is permitted to view.
2. The actor selects **Create**, **Read**, **Update**, or **Delete**. The system requests the relevant input or hub identifier.
3. For Create or Update, the actor submits hub details and a kitchen capacity setting. The system checks authorization, required data, value validity, and any confirmed uniqueness rules.
4. For Read, the system retrieves and displays the selected hub and its capacity setting.
5. For Create or Update, the system records the validated values and returns the resulting hub details.
6. For Delete, the system checks the confirmed removal policy and dependencies, applies the permitted action, and returns the outcome.

Steps 3 and 6 describe candidate system behaviour. Their exact validation thresholds, dependencies, and retention rules are **To Confirm**.

### Alternative flows

- **A1 — Create:** At step 2, the actor chooses Create and enters a new hub. The system creates it after successful checks and returns its identifier and recorded capacity setting.
- **A2 — Read:** At step 2, the actor chooses Read. The system returns the selected hub without changing it.
- **A3 — Update capacity or hub details:** At step 2, the actor chooses Update. The system shows current values, accepts the edited values, checks them, and returns the updated record. Whether capacity changes affect existing orders is **To Confirm**.
- **A4 — Delete or archive:** At step 2, the actor chooses Delete. The system first applies the confirmed dependency and retention policy. The choice between hard deletion, soft deletion, and blocking removal is **To Confirm**; this draft does not prescribe one.
- **A5 — List/search:** The actor filters the hub list. Search fields, pagination, and sorting are **Proposed / To Confirm**.

### Exception flows

- **E1 — Unauthorized:** At any operation, the actor lacks the required permission. The system rejects the request without disclosing or changing protected hub data.
- **E2 — Invalid input:** A required value is absent or a capacity value fails its confirmed validation rule. The system identifies the invalid field and makes no change. Capacity units and limits are **To Confirm**.
- **E3 — Hub not found:** A selected identifier is absent or unavailable. The system reports that the hub cannot be found and asks the actor to refresh the list.
- **E4 — Duplicate or conflicting record:** A confirmed unique identifier conflicts with an existing hub, or another user changes the record before the write. The system rejects the stale/conflicting write and returns the current state where authorized. Uniqueness keys and concurrency policy are **To Confirm**.
- **E5 — Removal blocked:** A confirmed dependency or retention rule prevents Delete. The system explains the block and preserves the record. Which dependencies block removal is **To Confirm**.
- **E6 — Persistence or response failure:** The system reports a failed write. If a response is lost after a possible write, the actor reads the record before retrying to avoid duplicate creation or unintended repeated changes.
