# UC16 — Produce Management Reports

**Author:** Võ Tấn Tài — 524H0126

## Scope and evidence

The Team F4 proposal, workbook, and presentation identify UC16 as management reporting owned by Võ Tấn Tài. They mention sales, hub workload and delivery performance. Workbook Client Q&A Q5 asks which metrics and reporting periods are required; its proposed answer and Assumption A-05 suggest day/week views, but both remain unconfirmed. The SaigonBite Case Study, Final Project Requirements and RAD Report Template were not available during the repository audit. Thus the report definitions below are a **Proposed / To Confirm** analysis draft, not an approved KPI specification.

## Fully developed use case description

| Field | Description |
|---|---|
| Goal | Allow an authorized Manager to request and inspect a management report for a selected scope and period. |
| Primary actor | Manager, as named in Team F4's proposal and workbook. The specific role permissions and visibility limits are **To Confirm**. |
| Trigger | The Manager opens reporting and requests a report. |
| Stakeholders | Manager needs dependable operational information; Admin and operational staff need records to be interpreted consistently; customers require their personal data to remain protected. |
| Preconditions | The Manager is authenticated and authorized for the requested report and scope (**permission matrix To Confirm**). Required source records are available. The selected report type and period are supported once confirmed. |
| Success postconditions | A report is produced from eligible source records with its scope/period and calculation basis identified. The request does not change orders, hubs, deliveries or payments. Saving or exporting the report is **To Confirm** and outside the confirmed minimum scope. |
| Minimal guarantee | Invalid, unauthorized, incomplete or failed requests do not mutate source records and do not expose protected data. The system communicates whether the result is empty, incomplete, or unavailable. |

### Main success scenario

1. The Manager opens management reporting. The system presents the report options and filters the Manager may access.
2. The Manager selects a report type, period and permitted scope. Candidate report types are sales, hub workload and delivery performance; exact options are **To Confirm**.
3. The system checks authorization and filter validity.
4. The system retrieves source records within the permitted scope and requested period.
5. The system aggregates values using the confirmed KPI definitions and checks whether source data is sufficiently complete for the requested result.
6. The system displays the report with labels for report type, period, scope and data status.

### Alternative flows

- **A1 — Different report type:** At step 2, the Manager selects sales, hub workload or delivery performance. The system applies that report's confirmed metric definitions and eligible record rules. All formulas and status inclusion rules are **To Confirm**.
- **A2 — No eligible records:** At step 4, no records match. The system displays an empty result with the selected filters and a clear no-data message; it does not substitute zero for an undefined metric.
- **A3 — Narrower scope or period:** At step 2, the Manager changes a filter. The system checks permission again and recalculates the report for the new scope. Whether day/week periods or individual hub filters are required is **To Confirm**.
- **A4 — Export:** If export is approved later, the Manager requests an export of the visible result. Format, content, privacy controls and retention are **To Confirm**; no export event is assumed in the current SSD.

### Exception flows

- **E1 — Unauthorized report or scope:** At steps 1–3, the Manager lacks access. The system rejects the request and reveals neither the report nor protected source data.
- **E2 — Invalid or unsupported filters:** At step 3, a period or scope is malformed, unsupported or logically invalid. The system identifies the problem and requests correction without generating a misleading result.
- **E3 — Missing or incomplete source data:** At steps 4–5, required records or status fields are unavailable or inconsistent. The system marks the report incomplete or unavailable according to a **To Confirm** data-quality policy; it never silently presents a complete report.
- **E4 — Retrieval or aggregation failure:** At steps 4–5, a source query times out or calculation fails. The system reports failure and does not present a partial result as complete.
- **E5 — Data changes during generation:** If concurrent writes affect the report, the system applies a documented snapshot/as-of policy (**To Confirm**) or reports that consistency cannot be guaranteed.

### Business rules and open decisions

| ID | Rule or decision | Status |
|---|---|---|
| BR16-1 | Only authorized Managers can access a report and its underlying scope. Exact roles, row-level scope and sensitive fields require confirmation. | Proposed / To Confirm |
| BR16-2 | Report values must have defined source records, filters, units and status inclusion rules. Sales, hub workload and delivery performance are candidate categories only. | To Confirm |
| BR16-3 | Reporting period and timezone must be specified. Day/week is the unconfirmed proposal in Q5/A-05. | To Confirm |
| BR16-4 | No-data, incomplete-data and processing-error results must be distinguishable from valid zero values. Exact data-quality thresholds are To Confirm. | Proposed / To Confirm |
| BR16-5 | Generating a report reads operational data and must not change it. Export, scheduling and storage are outside the confirmed scope. | Proposed / To Confirm |

## Traceability and boundary

Q5/A-05 in the Team Workbook is draft and has no lecturer answer. UC16 reads data produced by ordering, hub management and delivery; it does not create or correct those records. The domain vocabulary `Order`, `Hub` and `Shipper` follows the existing shared UC07/UC10 model. The exact report data sources and KPI formulas await source requirements or client confirmation.
